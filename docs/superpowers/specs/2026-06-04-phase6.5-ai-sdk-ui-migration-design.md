# Phase 6.5 — AI SDK UI + AI Elements 전환 설계

작성일: 2026-06-04
상태: 승인됨 (구현 plan 작성 대기)

## 배경 / 동기

Phase 6에서 채팅 스트리밍을 **수제 SSE 프로토콜**(FastAPI `sse-starlette` + 커스텀 이벤트
`token`/`message`/`blocked`/`confirmation_required`/`done`/`error`)과 **수제 프론트 파서**
(`lib/chat.ts`의 `fetch`+`getReader`+`split`)로 구현했다. 이 방식은 동작하지만:

- 프론트가 SSE 파싱을 직접 소유해 버그에 취약하다 (실제로 CRLF 구분자 미스매치로 무응답 버그 발생·수정한 이력 있음 → `[[sse-starlette-crlf-separator]]`).
- 메시지 상태/스트리밍/중단/에러 처리를 손으로 관리한다 (`upsertAssistant`, `busy` 등).

Vercel 공식 템플릿 `vercel-labs/ai-sdk-preview-python-streaming`이 입증하듯,
**Python FastAPI가 AI SDK v5 "UI Message Stream" 프로토콜을 직접 emit하고
`@ai-sdk/react`의 `useChat`가 직접 소비하는** 패턴은 공식·지원되는 길이다
(중간 Next 라우트 불필요). 이 전환으로 프론트의 파싱/상태 보일러플레이트를 SDK에
위임하고, AI Elements(shadcn 기반 prebuilt 컴포넌트)로 UI 완성도를 높인다.

핵심 통찰: **변환 코드는 사라지지 않고 프론트 → 백엔드로 자리를 옮긴다.**
프론트 `lib/chat.ts` 파서가 하던 일을 백엔드 번역기(`agent/ui_stream.py`)가 대신한다.

## 결정 사항 (브레인스토밍 확정)

1. **대체(Replace)** — 기존 `/chat/stream` + `lib/chat.ts` + `page.tsx`를 갈아끼운다. 공존 안 함. 학습 포인트는 git 히스토리에 남는다.
2. **AI Elements 도입(옵션 C)** — shadcn/ui 기반 prebuilt 컴포넌트로 UI 조립. Tailwind v4는 이미 있음. `Response`는 streamdown 마크다운 렌더.
3. **HITL 재개 = 스트리밍 재개(옵션 1)** — 승인/거절 후 재개된 답변도 UI Message Stream으로 흘려 `useChat`의 새 assistant 메시지로 이어진다.

## 아키텍처

```
브라우저 (Next.js)
  └─ useChat (@ai-sdk/react)
       │  prepareSendMessagesRequest 로 { message, thread_id, user_id } 만 전송
       ▼
FastAPI POST /chat/stream
  └─ agent/ui_stream.py 번역기
       agent.astream(stream_mode=["updates","messages"])
         → UI Message Stream 파트(SSE)로 매핑  (streaming.py 판별 헬퍼 재사용)
  └─ LangGraph create_agent + 미들웨어 (guardrail/PII/HITL/memory/할루시네이션) — 변경 없음
```

- **백엔드 에이전트/미들웨어는 손대지 않는다.** 오직 스트림 표현 계층만 교체한다.
- 새 모듈 `backend/agent/ui_stream.py`: `agent.astream` 이벤트를 UI Message Stream 파트
  딕셔너리로 변환하는 **순수 매핑 함수 + 제너레이터**. I/O 없음 → 단위 테스트 가능.
  기존 `streaming.py`의 `is_final_answer_chunk` / `is_search_tool_result` /
  `extract_interrupt_action`을 그대로 재사용한다.
- 현재 `routers/chat.py`의 `event_generator`(커스텀 프로토콜)는 제거하고,
  `/chat/stream`은 UI Message Stream을 반환하는 `StreamingResponse`로 재작성한다.

## 이벤트 → UI Message Stream 매핑

| 우리 에이전트 이벤트 | 내보낼 UI Message Stream 파트 |
|---|---|
| 시작 | `start { messageId }` |
| 일반 답변 토큰 (검색 미사용) | `text-start { id }` 1회 → `text-delta { id, delta }` ×N → `text-end { id }` |
| RAG 답변 (검색 사용, 버퍼링·할루시네이션 검사 후) | 검사 완료본을 `text-start` / `text-delta`(전체 1회) / `text-end` |
| 차단 (Before Guardrail) | 커스텀 데이터 파트 `data-blocked { reason }` (텍스트 없이 종료) |
| 환불 interrupt | 커스텀 데이터 파트 `data-confirmation { tool, args, thread_id }` (종료) |
| 정상 종료 | `finish` → `[DONE]` |
| 오류 | error 파트 |

설계 의도(유지): RAG 답변은 할루시네이션 검사가 전체 답변을 필요로 하므로 **버퍼링 후 1회 전송**
(토큰 스트리밍 안 함). 일반 답변만 토큰 스트리밍. 이는 Phase 6 동작과 동일하다.

> **검증 항목(plan 단계):** AI SDK v5의 정확한 파트 `type` 문자열, 커스텀 `data-*` 파트의
> wire 포맷, 필수 응답 헤더(`x-vercel-ai-ui-message-stream: v1` 등)는 **설치된 `ai` 패키지
> 문서/소스로 확인**한 뒤 코드에 반영한다 (CLAUDE.md "공식 문서" 규칙). 본 설계는 altitude만 고정한다.

## 메모리 (thread_id) 유지

`useChat`는 기본적으로 전체 메시지 히스토리를 매 요청 전송한다. 우리 백엔드는
LangGraph 체크포인터(`thread_id`)가 단기 기억을 들고 있으므로, **클라이언트는 마지막
사용자 메시지만 보내면 된다.**

- `DefaultChatTransport`의 `prepareSendMessagesRequest`를 커스터마이즈해
  요청 본문을 `{ message: <마지막 사용자 텍스트>, thread_id, user_id }`로 reshape한다.
- `thread_id`는 대화당 하나, 클라이언트가 보관 (현재 `useRef(crypto.randomUUID())`와 동일 개념).

## HITL 환불 흐름 (스트리밍 재개)

1. 사용자가 환불을 요청 → 에이전트가 `submit_refund_request` 직전 interrupt.
2. 번역기가 `data-confirmation { tool, args, thread_id }` 파트를 emit하고 스트림 종료.
3. 프론트 `components/refund-confirm-card.tsx`가 해당 데이터 파트를 읽어
   승인/거절 카드 렌더.
4. 승인/거절 클릭 → `POST /chat/confirm` 호출. 이 엔드포인트도 **UI Message Stream으로
   재작성**되어, `Command(resume=...)`로 재개된 답변을 스트리밍한다.
5. 재개된 답변은 `useChat`의 **새 assistant 메시지**로 이어붙는다 (일관된 스트리밍 UX).

> 구현 노트(plan 단계 확정): `/chat/confirm`의 재개 결과를 useChat에 흘리는 방법은
> useChat의 transport 또는 `sendMessage`로 confirm 엔드포인트를 호출하는 형태가 될 수 있다.
> 정확한 메커니즘은 `ai` v5 문서로 확인한다.

## 엔드포인트 변경

| 엔드포인트 | 변경 |
|---|---|
| `POST /chat/stream` | UI Message Stream 반환으로 **재작성** (커스텀 프로토콜 제거) |
| `POST /chat/confirm` | UI Message Stream 스트리밍 재개로 **재작성** (현재 JSON 반환 → 스트리밍) |
| `POST /chat` | **유지** (Phase 2 비스트리밍 경로, 기존 테스트 보존. 새 UI는 미사용) |
| `/upload`, `/documents`, `/pending`, `/approve`, `/refunds`, `/health` | 변경 없음 |

CORS는 현재대로 `localhost:3000/3001` 허용 유지.

## 프론트엔드 구조

- `app/page.tsx`: `useChat` + AI Elements `Conversation` / `Message` / `PromptInput` / `Response`.
- `components/refund-confirm-card.tsx`: `data-confirmation` 파트 렌더 + 승인/거절 → confirm 호출.
- `components/blocked-notice.tsx`: `data-blocked` 파트 렌더 (⚠️ 안내).
- `lib/chat.ts`: 수제 SSE 파서 **삭제**. transport 설정(`prepareSendMessagesRequest`) + 타입만 잔존, 대폭 축소.
- 신규 의존성: `ai`, `@ai-sdk/react`, AI Elements(shadcn 레지스트리로 컴포넌트 소스 레포에 생성), streamdown(AI Elements `Response`가 사용).

## 테스트 전략

- **백엔드 (pytest, 네트워크 없음):** `agent/ui_stream.py` 번역기 단위 테스트.
  가짜 `astream` 이벤트 시퀀스(일반 토큰 / 검색 ToolMessage+최종답변 / interrupt payload /
  차단)를 입력해 **기대하는 UI Message Stream 파트 시퀀스**가 나오는지 검증.
  `tests/test_streaming.py`의 무네트워크 방식을 그대로 따른다.
- **프론트:** `tsc --noEmit` 통과. 브라우저 4흐름 수동 E2E:
  ① 일반 답변 토큰 스트리밍 ② 차단 ③ RAG 답변 ④ 환불 승인→스트리밍 재개.
- **의존성 규칙:** 추가하는 모든 파이썬 import는 `python -W error::DeprecationWarning`로 검증.
  프론트 신규 패키지는 공식 문서 기준 설치.

## 위험 / 미해결

- AI SDK v5의 정확한 파트 wire 포맷과 커스텀 `data-*` 스펙은 설치 후 문서로 확정해야 한다(plan에서 처리).
- AI Elements가 레포에 생성하는 컴포넌트 소스 파일 수가 많다 (shadcn 방식). 학습 표면 증가는 수용한다.
- `/chat/confirm` 스트리밍 재개를 useChat에 매끄럽게 잇는 정확한 메커니즘은 plan에서 문서로 확정.
